## A. 工具参数级致命坑

### 6.1 `pg_restore` 的 `-f` 是【输出】文件，不是输入文件 ⛔

**症状**

```
pg_restore: error: input file is too short (read 0, expected 5)
```

**成因**

PostgreSQL 的 `pg_restore` 里，`-f` / `--file` 的含义是**把恢复结果写到哪个文件**，
**不是**"从哪个文件读"。误用 `-f` 时，它把归档当成输出目标，
于是尝试读取归档来"拷贝"到一个空文件里 → 读到 0 字节。

```
pg_restore --help
  -f, --file=FILENAME      output file name (- for stdout)
                            ↑ 注意这行
```

**正确用法**

```bash
pg_restore -d mydb --no-owner --no-privileges --clean --if-exists backup.dump
#                                                      ↑ 位置参数 = 输入归档
```

**额外坑**：`pg_restore` 不允许 `-d` 和 `-f` 同时给
（报 `options -d/--dbname and -f/--file cannot be used together`）。

**为什么隐蔽**：容器模式里 `docker cp` 明明成功、日志无异常，
只有 `pg_restore` 报"文件太短" —— 很容易误判成"备份文件损坏"，
实际上是参数用错了。

**规避**：归档一律走位置参数。

### 6.2 `set -euo pipefail` 会让"正常的空结果"终止脚本 ⛔

**症状**

脚本在"没有错误"的场景下莫名退出，且没有任何错误信息。

**成因**

```bash
set -euo pipefail
FATAL=$(grep "ERROR:" err.log | grep -viE "already exists" | head -10)
```

`grep -viE` 把所有内容都过滤掉了 —— 这正是"**没有致命错误**"的正常情况。
但 `grep` 没匹配到内容时退出码是 **1**，`pipefail` 把它传播出来，
于是这条**赋值语句**整体返回非零，`set -e` 直接终止脚本。

**同一个坑的变体**：

```bash
CONFLICT=$(grep -c "ERROR:" err.log 2>/dev/null || echo 0)
```

`grep -c` 在无匹配时**已经输出 `0`** 且退出码为 1，
`|| echo 0` 于是又追加一行 `0` → 变量变成 `"0\n0"` →

```
bash: [: 0
0: integer expression expected
```

**规避**

```bash
# 方案 A：管道整体兜底
FATAL=$({ grep "ERROR:" err.log | grep -viE "already exists" | head -10; true; })

# 方案 B：计数用 ; true 而不是 || echo
CONFLICT=$(grep -c "ERROR:" err.log 2>/dev/null; true)
CONFLICT=${CONFLICT%%$'\n'*}     # 或 head -1
```

**教训**：写 `set -euo pipefail` 脚本时，
**每一个管道赋值都要显式处理"空结果"这个正常情况**。

### 6.3 `docker exec` 不会解释 `psql` 的 `-d` ⛔

**症状**

查询连到了错误的数据库，表现为"表不存在"或"数据不对"。

**成因**

```bash
docker exec sse-postgres-1 psql -U sse -d sse_new
```

这里的 `-d` 是 **psql 的 `--dbname`**，真实 `docker exec` 会原样传给容器内命令。
但如果自己写 `docker` 模拟脚本（或某些封装工具）把 `-d` 当成 Docker 的
`--detach` 处理，参数就被吞掉了。

**规避**

- 真实环境：用 `docker exec` 时明确区分 Docker flag 与容器内命令的 flag
- 若写模拟/封装层：只在**容器名之前**解析 `-d`/`--detach`

### 6.4 容器内路径与宿主机路径不是一回事 ⛔

**症状**

```bash
docker cp backup.dump sse-postgres-1:/tmp/x.dump   # 成功
docker exec sse-postgres-1 pg_restore -d sse -f /tmp/x.dump
# → error: input file is too short
```

**成因**

宿主机上的 `/tmp/x.dump` 和容器里的 `/tmp/x.dump` 是**两个不同的文件**。
需要"先拷进去再读"的路径必须一致；需要"读出来"的操作（如 `pg_dump`）
则必须在**容器内**完成再 `docker cp` 取回。

**三条必须遵守的规则**：

| 场景 | 做法 |
|---|---|
| 宿主机 SQL 文件 → 容器内 psql | `docker exec -i … psql < host.sql`（stdin） |
| 宿主机归档 → 容器内 pg_restore | `docker cp host.dump ctr:/tmp/x.dump`，然后 `pg_restore … /tmp/x.dump` |
| 容器内 pg_dump → 宿主机 | `docker exec ctr pg_dump -Fc -f /tmp/x.dump` → `docker cp ctr:/tmp/x.dump .` |

**为什么 `pg_dump` 不能重定向 stdout**：custom 格式（`-Fc`）要求**可 seek 的文件**，
管道/重定向会破坏它。

## B. Shell 脚本陷阱

### 6.5 纯文本消息混进了重定向的 SQL 文件 ⛔

**症状**

```
ERROR: syntax error at or near "跳过 identity_mappings"
```

**成因**

```bash
# ❌ 错
echo "跳过 identity_mappings" >> "$SQLTMP"
```

shell 的 `echo` 输出被追加进了 SQL 文件，SQL 解析器当然报错。

**规避**：所有面向用户的打印走 **stderr**，SQL 内容只进 SQL 文件。

```bash
# ✅
echo "跳过 identity_mappings" >&2
```

---

### 6.6 `TARGET_DB=""` 初始化写在参数解析之后 ⛔

**症状**：脚本连到了错误的库，或者 `--target-db` 参数被无视。

**成因**

```bash
# 参数解析
TARGET_DB="sse"
...
# ❌ 后面的默认值初始化把它重置了
TARGET_DB="${TARGET_DB:-}"      # 在解析之后
```

**规避**：所有默认值初始化必须在**参数解析之前**，或者干脆不重复初始化。

---

### 6.7 回滚测试用固定 id 做基线标记 ⛔

**症状**：换个数据源后，回滚测试的基线标记找不到，测试逻辑崩掉。

**成因**

```bash
# ❌ 写死了某个具体 id
BASE_ID="1081eb9b-d440-4877-b133-031a8b835962"
```

**规避**：动态发现基线。

```bash
BASE_ID=$(psql -tAc "SELECT id FROM expense_categories LIMIT 1")
```

---

### 6.8 SQL 字面量改用 `E'...'` 后，下游解析器要同步 ⛔

**症状**：角色→UUID 转换找不到映射值。

**成因**

生成端改成 `E'...'` 转义形式后，解析端如果只认普通 `'...'`，就解不出内容。
而且 `approval_chain` 的值里**本身还带 SQL quoting 和额外转义**，
需要同时支持两种字面量：

```python
def unquote_literal(tok):
    """同时处理 '...' 和 E'...' 两种 PostgreSQL 字面量。"""
```

**规避**：改生成格式时，**同步检查所有解析该格式的下游代码**。

## C. 数据格式与语义坑

### 6.9 离线提取的 `schema.sql` 不含自定义唯一约束 ⛔

**症状**：回滚测试的注入不触发 —— 靠唯一约束制造失败的逻辑完全没生效，
导入"成功"了，测试判定 FAIL。

**成因**

`pg_offline_export.py` 导出的 `schema.sql` 只有**表定义**（列、类型、DEFAULT），
**没有 UNIQUE / CHECK / FOREIGN KEY**。

**后果**

- 靠唯一约束做注入点，在恢复出来的目标库上**根本不会触发**
- 目标库的唯一约束来自它**自己的 migration**，与源库 schema.sql 无关

**规避**：注入点改用 **PostgreSQL 内建约束**（`NOT NULL`）——
任何目标库都有，稳定生效。

**顺带的设计启示**：备份包的 `schema.sql` 定位是
"**目标库还没有这些表时的建表依据**"，而不是"目标库约束的权威来源"。
目标库约束由目标系统自己的 migration 决定。

---

### 6.10 CSV 里 NULL 与空字符串必须区分 ⛔

**症状**：`parent_id`（应为 NULL）和 `password_hash`（应为空字符串）混在一起，
恢复后语义变了。

**成因**

`COPY` 默认把 NULL 输出成**空字段**，与空字符串完全无法分辨。

**规避**

```sql
COPY (SELECT * FROM t) TO 'f.csv' WITH (FORMAT csv, HEADER, NULL '\N')
```

生成端用 `\N` 标记 NULL，空字段仍是空字符串 —— 二者严格可区分。

---

### 6.11 行数必须按 CSV 记录数统计 ⛔

**症状**：报告的行数比实际高，误导判断。

**成因**

`jsonb` / `text` 字段含换行时，**一条记录占多个物理行**：

```
notification_logs:  物理行 135  ← wc -l 的结果，错
                    实际记录 49  ← csv.reader 的结果，对
```

**规避**

```python
import csv
with open(path, newline='', encoding='utf-8') as f:
    count = sum(1 for _ in csv.reader(f)) - 1   # 减掉表头
```

**并且**：最终必须用 PostgreSQL 自身的 `count(*)` 逐表交叉核对。
本项目已做，确认无数据丢失。

---

### 6.12 一条 INSERT 必须只占一个物理行 ⛔

**症状**：按行 grep 的导入器只取到第一行 → SQL 残缺 → 数据不完整。

**成因**

`system_messages.body` 是多行变更日志。直接内嵌换行，一条 INSERT 横跨多行。

**规避**

统一用 PostgreSQL `E'...'` 转义字符串形式，把换行/回车/制表符转成
`\n` / `\r` / `\t`，保证**一条逻辑记录 = 一个物理行**。

**收益**：下游可流式处理，`grep -c "^INSERT INTO"` 直接数记录数。

---

### 6.13 数组列不能当字符串塞 ⛔

**症状**：`invalid input syntax for type text[]`。

**成因**

`target_roles` 是 `text[]`，CSV 里是 `{admin,dept_approver,finance}`。
当成字符串 `'{...}'` 塞进 `text[]` 列会报错。

**规避**：按数组字面量生成，元素含逗号/花括号/空格时**逐个加双引号**。

## D. SSE 业务语义坑

### 6.14 `storage_key` 带双重 bucket 前缀 ⛔

**症状**：MinIO 里找不到对象，或对象写到了错误的位置。

**源码依据**（`packages/api/src/routes/experiments.ts`）

```ts
const storageKey = `invoices/${req.params.id}/${itemId}_${Date.now()}.${ext}`;
await minio.upload(storageKey, 'invoices', ...);   // → putObject(bucket='invoices', key=storageKey)
```

⇒ **磁盘全路径 = `bucket + '/' + storage_key`**：

```
storage_key (DB) : invoices/1081eb9b-…/xxx.pdf
bucket      (DB) : invoices
磁盘全路径        : invoices/invoices/1081eb9b-…/xxx.pdf   ← 双层
```

> **早期注释断言"storage_key 本身是完整 object key，不要再拼 bucket" —— 是错的。**

---

### 6.15 `avatar_url` 不拼 bucket ⛔

**源码依据**

```ts
await minio.getObject(user.avatarUrl, 'avatars');   // bucket='avatars', key=avatar_url
```

`users.avatar_url` 存的是 MinIO 的 **key**（不含 bucket），
所以头像比对时**不能**再拼一层 bucket。

> 6.14 和 6.15 方向相反，**必须分别处理**，不能套用同一条规则。

---

### 6.16 `approval_records.approver_id` 的角色→UUID 漂移 ⛔

**症状**

```
ERROR: invalid input syntax for type uuid: "finance"
```

**成因**

旧盘线上实际是 `character varying(50)`，存角色名（`admin` / `finance`）；
但旧盘自己的 migration 文件写的是 `UUID`。
当前 SSE 的 migration 已改回 `uuid REFERENCES users(id)`。

**权威映射来源** = `approval_rules.approval_chain`（审批链创建时绑定了实际审批人）：

```json
{"role": "admin",   "assigneeId": "3e856835-07c0-41b8-9ae1-f33ef17ce80c", "assigneeName": "系统管理员"}
{"role": "finance", "assigneeId": "a7e2c5f4-3e15-4197-bb8f-7c36456b4cf1", "assigneeName": "王钰"}
```

**比"按 `users.role` 反查"准确** —— `admin` 角色有 2 个用户，
但审批链指定了实际那个人。

**规避**：显式转换 + 留痕到 `meta/semantic_transform.json`，**不静默改写**。

---

### 6.17 目标库可能比源数据多/少列 ⛔

**症状**：INSERT 报"列不存在"；或数据写到了错误的列。

**实例**：旧盘 `expense_reports` 有 `description` 列，当前 migration 已删除。

**规避**：`filter_insert_columns.py` 按**目标库真实列**自动对齐：

| 情况 | 处理 |
|---|---|
| 目标库没有该列 | 剔除 |
| 目标库有、源没有 | 用 DEFAULT / NULL 补齐 |
| 目标库该列 NOT NULL 且无默认值 | **直接失败**，不静默丢数据 |

## E. 测试与验证陷阱

### 6.18 回滚测试的"假通过" ⛔ ⛔

**症状**：测试报告"回滚成功"，但实际上什么都没验证。

**成因**

```bash
BEFORE_USERS=$(…)   # 空 —— 目标库本来就没表
AFTER_USERS=$(…)    # 空 —— 回滚后确实没表
[ "$BEFORE_USERS" = "$AFTER_USERS" ] && echo "✅ 回滚成功"
```

两个空串相等 → 判定成功。**但基线本身就是无效的**。

**规避**：加基线有效性断言。

```bash
if [ -z "$BEFORE_USERS" ] || [ "$BEFORE_USERS" = "0" ]; then
  echo "  ❌ 基线无效：目标库 users 为空，无法验证回滚"
  FAIL=1
fi
```

**而且**：跑回滚测试前**必须先跑一次正常导入**建立基线。

> 这是本次工作中最容易骗过自己的一个坑 —— 它在"空库"场景下报告绿色。

---

### 6.19 验证器复用导入器的中间产物 ⛔

**症状**：导入逻辑有 bug 时，验证也会一起错，验证形同虚设。

**规避**：`verify_sse_restore.sh` **完全独立**实现 ——
重新读备份包、重新查目标库、重新算 checksum，做四类交叉校验。

---

### 6.20 注入故障后没重算包内 checksum ⛔

**症状**：导入脚本在完整性校验阶段就拒绝执行，注入根本没跑到。

**成因**：注入故障修改了包内文件，但 `meta/checksums.sha256` 还是旧的。

**规避**：注入后立即重算。

```bash
( cd "$BROKEN" && find . -type f ! -path './meta/checksums.sha256' -print0 \
    | sort -z | xargs -0 sha256sum > meta/checksums.sha256 )
```

---

### 6.21 `DROP SCHEMA public CASCADE` 会连带删掉扩展 ⛔

**症状**：回滚后 `uuid_generate_v4()` 不存在，相关功能报错。

**成因**

```sql
DROP SCHEMA public CASCADE;
```

扩展装在 `public` schema 里，被一起删掉了。

**规避**：**建表前**和**回滚后**都要补建：

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS "pgcrypto";
```

## F. 安全与凭据风险

### 6.23 旧盘写入的隐蔽性 ⚠️

**症状**：`postgres --single` 跑完，源 PGDATA 的 7 个文件被改了。

**实测被改的文件**：`pg_control`、`pg_wal/*`、`pg_xact/*` 等。

**规避**

- **永远在副本上跑**
- 提取前后核验原盘：

```bash

# 预期：无输出
```

**本项目实测结果**：1,379 个原始文件 **0 修改**（旧盘 ext4 `ro` 挂载）。

### 6.24 共享目录上的测试残留 ⚠️

**症状**：上传到共享目录的包里混进了 `.rollback-<时间戳>/` 目录，
里面是**测试过程的备份**，包含旧配置的副本。

**成因**：本地跑回滚测试后没清理，就直接打包上传。

**规避**：上传前清理 + 检查
