## 1. 测试策略

这套能力的测试分五层，每层验证一个不同的失效模式：

```
L1  提取正确性     会不会丢数据？
L2  提取无副作用   会不会改坏旧盘？
L3  包完整性       搬运过程中会不会损坏？
L4  恢复正确性     数据能不能正确进目标系统？
L5  回滚能力       失败能不能退回去？
```

外加一层：**分发完整性**（复制到共享盘 / 目标机后是否还一致）。

---

## 2. 各层测试手段

### 2.1 L1 提取正确性

| 手段 | 做法 | 通过标准 |
|---|---|---|
| 记录数交叉核对 | 用 `csv.reader` 统计 CSV 记录数，与 PostgreSQL `count(*)` 逐表比对 | 完全一致 |
| 物理行数**不可用** | `wc -l` 会因内嵌换行虚高 | —— |
| 表清单核对 | 比对 `meta/tables_present.txt` 与实际导出表 | 一致 |
| 对象数核对 | `meta/minio_counts.txt` 与实际导出对象数 | 一致 |
| 关联完整性 | 从数据库的 `storage_key`/`avatar_url` 反查导出对象 | 全部命中 |

**实例（真实旧盘）**：

```
15 张业务表全部核对通过
notification_logs: 物理行 135 / 实际记录 49   ← 物理行数是错的
最终确认：264 行，无数据丢失
```

### 2.2 L2 提取无副作用

```bash
# 提取前记录原 PGDATA 文件状态
find "$PGDATA" -type f -printf "%T@ %s %p\n" | sort > /tmp/pgdata_before.txt

# 提取后
find "$PGDATA" -type f -printf "%T@ %s %p\n" | sort > /tmp/pgdata_after.txt

diff /tmp/pgdata_before.txt /tmp/pgdata_after.txt
# 预期：无差异
```

**实测结果**：1,379 个文件 **0 修改**（ext4 `ro` 挂载，物理上也无法写入）。

### 2.3 L3 包完整性

```bash
cd olddisk-package
sha256sum -c meta/checksums.sha256
# 预期：44 个文件全部 ": OK"
```

**注意**：`checksums.sha256` 不含自身（生成时排除）。

### 2.4 L4 恢复正确性

由 `verify_sse_restore.sh` 独立执行四类交叉校验：

```
① 表行数     15/15
② 桶对象数    3/3
③ 对象 checksum 16/16
④ 数据库↔对象关联 15/15
```

**关键设计**：验证器**不复用导入器的任何中间产物**，
独立重新读包、重新查库、重新算 hash。

### 2.5 L5 回滚能力

| 测试 | 注入点 | 验证内容 |
|---|---|---|
| `test_rollback.sh` | DB 阶段：违反 NOT NULL 约束 | PG 自动回滚 + 快照还原 + MinIO/配置还原 |
| `test_rollback_minio.sh` | MinIO 阶段：bucket 上传失败 | MinIO 清空还原 + DB 还原 + 配置还原 |

**判定方式**：导入前后状态**完全一致**（行数、对象数、基线标记）。

**防假通过**：基线为空时直接判 FAIL（见 06 文档 6.18）。

### 2.6 分发完整性

```bash
# 102 上：用包自带的 checksum 校验
sha256sum -c meta/checksums.sha256

# 与本机逐文件比对 SHA-256
```

## 6. 回归测试建议（并入 SSE 后）

### 6.1 需要补的单测

并入 monorepo 时，建议补以下单测（当前全部依赖端到端脚本测试）：

| 模块 | 测试点 |
|---|---|
| `sql-literal` | 换行/引号/反斜杠/数组/NULL 的字面量生成 |
| `column-align` | 多列、少列、NOT NULL 缺列时失败 |
| `xlmeta` | 用真实 `xl.meta` 样本做 fixture，测内联/外置两条路径 |
| `semantics` | 角色→UUID 映射、`E'...'` 字面量解析 |
| `importer` | 删除顺序（逆序）、事务边界 |

### 6.2 保留的端到端测试

现有两个回滚脚本 + 验证脚本**必须保留为回归测试**，
它们是唯一能验证"真能退回去"的东西。

建议在 CI 里跑（用一次性容器，不碰生产库）：

```yaml
# .github/workflows/backup-e2e.yml（示例）
- run: docker compose -f docker-compose.test.yml up -d
- run: pnpm sse-backup restore --from ./fixtures/pkg --target-db sse_test
- run: pnpm sse-backup verify  --from ./fixtures/pkg --target-db sse_test
- run: pnpm sse-backup test:rollback --from ./fixtures/pkg --target-db sse_test
```

**fixture 用真实的 `olddisk-package`** —— 真实数据才能暴露真实问题
（比如 `expense_reports` 的列漂移、`approver_id` 的类型漂移）。

### 6.3 定期演练

**建议每季度做一次完整恢复演练**，流程见
[05-运维手册.md](05-运维手册.md) 第 6.3 节。

## 7. 已知测试缺口

| 缺口 | 风险 | 建议 |
|---|---|---|
| 无真实 Docker 上的 container 模式自动化测试 | 本机用模拟器，行为可能与真实 Docker 有差异 | 在目标机或 CI 补一次真实 Docker 跑通 |
| 无 TS 单元测试（当前是 shell/python） | 改动的回归风险高 | 并入 monorepo 时补 |
| 无增量导出测试 | 增量是未来能力 | 实现时同步补 |
| 无跨 major 升级测试 | 当前明确不支持 | 保持不支持，引导用官方 `pg_upgrade` |
| 无大库性能测试 | 当前规模很小（264 行） | 生产规模下需重新评估串行导出 |
