## 1. 设计目标

### 1.1 功能目标

在**不启动旧系统任何服务**、**不写入旧盘一个字节**的前提下，
把 SSE 的 PostgreSQL 数据与 MinIO 对象完整、可用、可验证地恢复到新系统。

### 1.2 非功能目标

| 目标 | 具体要求 |
|---|---|
| 零副作用 | 旧盘只读；所有写操作在副本或目标系统上 |
| 可离线搬运 | 产物是纯文件目录，不依赖任何特定运行环境 |
| 可验证 | 每个产物自带 checksum；恢复后独立可校验 |
| 可回滚 | 恢复失败必须能自动还原到恢复前状态 |
| 可审计 | 所有语义转换留痕，不静默改写数据 |
| 可移交 | 零隐式环境依赖，脚本自解释，文档完整 |

### 1.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 增量导出 / 时间点恢复 | 当前场景是灾难恢复，全量足够；增量需 WAL 归档，复杂度高 |
| 跨 major 版本自动升级 | PostgreSQL major 升级有官方 `pg_upgrade`，自研风险大于收益 |
| 加密备份包 | 属于分发层职责；应在传输通道加密，而非包内自研 |
| 在线热备份 | 与既有逻辑迁移层重复，优先用 `pg_dump` |

## 2. 架构设计

### 2.1 三层分离

整套能力拆成三层，每层职责单一、可独立测试、可独立替换：

```
┌─────────────────────────────────────────────────────────────────┐
│  L3  接入层    CLI / API / SSE monorepo 集成                      │
│      import_sse_data.sh · verify_sse_restore.sh · (未来 CLI)      │
├─────────────────────────────────────────────────────────────────┤
│  L2  恢复层    备份包 → 运行中系统                                 │
│      列对齐 · 语义转换 · 单事务导入 · 快照 · 自动回滚 · 独立验证    │
├─────────────────────────────────────────────────────────────────┤
│  L1  取证层    旧盘 → 备份包                                      │
│      PGDATA 解析 · xl.meta 解析 · CSV 导出 · 语义清洗 · 打包      │
└─────────────────────────────────────────────────────────────────┘
```

**为什么这样分**：

- L1 只关心"怎么把字节变成结构化数据"，不关心目标系统长什么样 → 可复用于任何目标
- L2 只关心"怎么把结构化数据放进目标系统"，不关心数据从哪来 → 可复用于任何来源
- L3 负责编排与用户界面

**关键收益**：L1 产出的包可以被 L2 导入，也可以被别的工具消费；
L2 的导入器既能吃 L1 的包，也能吃在线 `pg_dump`/`mc mirror` 的产物。

### 2.2 与既有逻辑迁移层的关系

SSE 项目里已有一套"在线导出/导入"能力（`export_sse_data.sh`），
本次新增的是"离线取证层"。两者**互补而非替代**：

```
                  ┌─────────────────────────────┐
   源系统健康     │   在线层（既有）              │──▶ 备份包
   （服务可启动）  │   pg_dump / mc mirror        │      ▲
                  └─────────────────────────────┘      │
                                                      同一格式
                  ┌─────────────────────────────┐      │
   源系统损坏     │   离线层（本次新增）          │──▶ 备份包
   （起不来）     │   PGDATA 解析 / xl.meta 解析  │      │
                  └─────────────────────────────┘      │
                                                      │
                  ┌─────────────────────────────┐      │
   目标系统       │   恢复层（本次新增 + 复用）   │◀─────┘
                  │   列对齐 · 导入 · 验证 · 回滚  │
                  └─────────────────────────────┘
```

**选层判据**：

| 条件 | 用哪层 |
|---|---|
| 旧盘能正常起服务 | 在线层（`pg_dump` 更简单可靠） |
| 旧盘起不来 / 只有文件 | 离线层 |
| 需要跨 major 升级 | 在线层 + 官方 `pg_upgrade` |
| 需要保留原始字节做取证 | 离线层 |

## 3. 数据模型

### 3.1 备份包（Backup Package）格式

备份包是一个**纯目录**，无压缩、无二进制封装，便于人工检视和分卷传输。

```
olddisk-package/
├── manifest.json               包级元信息（版本、来源、时间、统计）
│
├── pg/                         数据库层
│   ├── schema.sql              源库完整表定义（仅列/类型/默认值）
│   └── table_<name>.sql        每张表一个文件，每条 INSERT 占一行
│
├── minio/                      对象层
│   ├── invoices/invoices/<id>/<file>.pdf     ← 保留原始目录结构
│   ├── payment-receipts/payment-receipts/…
│   └── avatars/avatars/…
│
├── meta/                       审计与校验元数据
│   ├── checksums.sha256        包内全部文件的 SHA-256（不含自身）
│   ├── table_counts.txt        每表行数
│   ├── minio_counts.txt        每桶对象数
│   ├── tables_present.txt      实际提取到的表清单
│   ├── semantic_transform.json 语义转换记录（谁被改、为什么、改成什么）
│   ├── link_check.txt.*        数据库↔对象关联的引用统计
│   └── export_meta.sh          导出源环境（主机、库名、端口）
│
└── files/                      配置文件（可选恢复）
    ├── ai-config.json
    ├── ai-test-history.json
    └── env.local               ← 原 .env 改名，避免覆盖目标 .env
```

**设计要点**：

1. **`pg/` 与 `minio/` 分离** —— 两个存储独立演进，一方失败不影响另一方
2. **`minio/` 保留原始目录结构** —— 对象内容与 `storage_key` 语义直接对应，无需查表
3. **`meta/` 独立于数据** —— 数据文件损坏不影响审计信息
4. **`semantic_transform.json` 显式记录改写** —— 杜绝"静默丢数据"
5. **`env.local` 改名** —— 防止导入时覆盖目标系统已有的 `.env`

### 3.2 表级数据格式

每张表一个 `.sql` 文件，每条记录一行 INSERT：

```sql
INSERT INTO public.users ("id","email","name",…) VALUES ('…','…','…');
```

**为什么坚持"一条 INSERT 一行"**：

- 下游可按行 `grep` / `awk` 做流式处理，无需完整的 SQL 解析器
- 可用 `grep -c "^INSERT INTO"` 直接数记录数
- 单行出错可精确定位到某条记录

**为什么用 `E'...'` 转义形式**：

`system_messages.body` 是多行变更日志，直接内嵌换行会让一条 INSERT 横跨多行，
破坏上述性质。统一用 `E'...'` 把换行/回车/制表转成 `\n`/`\r`/`\t`。

**NULL 表示**：源数据导出时用 `COPY … WITH (FORMAT csv, HEADER, NULL '\N')`，
`\N` 表示 NULL，空字段表示空字符串 —— 二者严格可区分。

### 3.3 语义转换模型

源数据与目标 schema 之间存在**语义级**（而非仅结构级）的差异。
本项目实测到 2 类：

| 类型 | 实例 | 处理 |
|---|---|---|
| 类型不兼容 | `approval_records.approver_id` 源为 `varchar(50)` 存角色名，目标为 `uuid` | 角色名 → UUID 显式映射 |
| 集合类型 | `target_roles` 目标为 `text[]`，源 CSV 为 `{admin,finance}` | 按数组字面量生成，逐元素加引号 |

语义转换遵循三条原则：

1. **权威来源优先** —— 角色→UUID 的映射取自 `approval_rules.approval_chain.assigneeId`
   （审批链创建时绑定了实际审批人），而不是按 `users.role` 反查
2. **留痕可审计** —— 每一条改写写进 `meta/semantic_transform.json`
3. **失败不静默** —— 无法映射的值直接报错，不丢数据、不填默认值蒙混过关

## 4. 关键技术决策

### 4.1 决策 1：PGDATA 解析用 `postgres --single` 单用户模式

**问题**：要拿到 PostgreSQL 里的业务数据，常规做法是起服务连上去 dump。
但旧盘起服务有风险（可能损坏数据、可能误写）。

**候选方案**：

| 方案 | 可行性 | 结论 |
|---|---|---|
| 起服务 + `pg_dump` | 旧盘挂载后服务启动会写 WAL/控制文件 | ❌ 违反零写入 |
| 解析 heap 文件自己实现 | 需要懂 PG 存储格式，极易出错 | ❌ 不现实 |
| **`postgres --single`** | 单用户模式，只处理当前数据库，不监听端口、不做 checkpoint | ✅ 采用 |

**`--single` 的关键性质**：

- 不需要网络、不需要共享内存、不启动任何后台进程
- 仍然会写少量文件（`pg_control`、`pg_wal`、`pg_xact` 等，实测 7 个）
  → **必须在副本上运行**

**实测**：在 PGDATA 完整副本上运行，1,379 个原始文件**零修改**。

**版本约束**：二进制 major 版本必须与 PGDATA 一致（旧盘是 16，用 PostgreSQL 16.15）。
跨 major 会直接拒绝启动。

### 4.2 决策 2：MinIO 数据用 xl.meta 逆向解析，不用官方 SDK

**问题**：MinIO 没有"离线导出对象"的官方工具；起 MinIO 服务读旧卷也有写入风险。

**逆向成果**（详见 [02-导出功能设计.md](02-导出功能设计.md)）：

- `xl.meta` 魔数 `584c3220` / ASCII `XL2 `，v2 格式
- msgpack 编码，entries 从 offset **8** 开始（`obj[0]` 是嵌套的完整 `V2Obj` stat）
- 对象内容有两种布局：
  - **内联**（小对象）：`MetaSys` 含 `x-minio-internal-inline-data=true`
    → payload 边界 `header_len = len(blob) - stat.Size`（实测恒 32 字节）
  - **外置**（大对象）：`MetaSys` 为空 → 内容在 `<objdir>/<DDir-UUID>/part.N`

**代价与收益**：逆向成本高，但换来了"完全离线 + 零依赖"的提取能力，
且能取回**原始字节**（不做格式转换），对取证场景价值很高。

### 4.3 决策 3：导入用单事务 + 快照双保险

导入失败要能还原。有两个层次的保障：

```
第 1 层：单事务
    BEGIN;
    DELETE FROM ... （按依赖逆序）
    INSERT INTO ... × 264
    COMMIT;
    → 中途任何错误，PostgreSQL 自动 ROLLBACK，库回到导入前状态

第 2 层：快照 + EXIT trap
    导入前 pg_dump 快照 → .rollback-<时间戳>/backup.dump
    导入前 MinIO 全量备份 → .rollback-<时间戳>/minio/
    EXIT trap 捕获失败 → 用快照还原
```

**为什么两层都要**：单事务只保护数据库，不管 MinIO；
快照能保护 MinIO，但 pg_dump/pg_restore 本身可能失败（例如磁盘满）。
两层独立，互为兜底。

**删除顺序**：必须按导入顺序的**逆序**删，否则 `DELETE FROM users` 会被
外键约束挡住。也不能用 `TRUNCATE … CASCADE` —— 那会级联清空别的表。

### 4.4 决策 4：列对齐按目标库真实列自动做

源 schema 与目标 schema 会漂移（源多列、目标多列都可能出现）。

处理策略：

| 情况 | 处理 |
|---|---|
| 目标库没有该列 | 剔除（实测：`expense_reports.description`） |
| 目标库有、源没有 | 用 DEFAULT / NULL 补齐 |
| 目标库该列 NOT NULL 且无默认值 | **直接失败**，不静默丢数据 |
| 类型不兼容 | 转语义转换层处理（见 3.3） |

**为什么自动做**：目标库的列由它自己的 migration 决定，备份包不应该假设目标结构。
自动对齐让同一个包能导入不同版本的目标库。

### 4.5 决策 5：验证独立于导入

验证脚本 `verify_sse_restore.sh` **不复用导入脚本的任何中间产物**，
它重新读备份包、重新查目标库、重新算 checksum，做四类交叉校验：

```
① 15/15 张表行数一致
② 3/3  个 bucket 对象数一致
③ 16/16 个对象内容 SHA-256 一致
④ 15/15 条数据库↔MinIO 关联命中
```

**为什么强调独立**：如果验证复用导入时的统计，导入逻辑有 bug 时验证也会一起错。
独立实现才能发现"导入成功了但数据不对"。

### 4.6 决策 6：容器模式（宿主机无 psql 也能跑）

生产环境 PostgreSQL 在 Docker 容器里，宿主机通常没装 `postgresql-client`。
本项目**明确不要求在宿主机装任何东西**，所有 PG 命令走 `docker exec`。

这带来几个非平凡约束（详见 [06-踩坑与已知问题.md](06-踩坑与已知问题.md)）：

| 约束 | 处理 |
|---|---|
| 宿主机 SQL 文件容器内不可见 | `docker exec -i … psql < file`（stdin 传输） |
| `pg_dump` custom 格式要求可 seek 文件 | 容器内 `pg_dump -f /tmp/x.dump` → `docker cp` 取回 |
| `pg_restore` 的 `-f` 是**输出**文件 | 归档走**位置参数** |
| `DROP SCHEMA public CASCADE` 会删掉 `uuid-ossp` | 建表前与回滚后都补建扩展 |

统一用 `PG_CONTAINER` 环境变量开关，host / container 两套模式共用同一份逻辑。

## 5. 数据流详图

### 5.1 导出

```
旧盘 (ro)
 ├─ sse_pgdata/PGDATA ──cp──▶ /tmp/pgdata-work (副本)
 │                              │
 │                              └─ postgres --single ──COPY TO──▶ CSV
 │                                                        + schema.sql
 │                                                        + 表清单/行数
 │
 └─ sse_miniodata/
     ├─ <bucket>/<key>/xl.meta ──解析──▶ stat(Size/MetaSys/DDir/ETag)
     │                                    │
     │                                    ├─ inline ──▶ payload 边界推导
     │                                    └─ DDir ──▶ <uuid>/part.N
     │
     └───────────────────────────────────▶ 原始对象文件

        ↓ build_import_package.py
        ↓   · CSV → 单行 INSERT
        ↓   · 语义转换（角色 → UUID）
        ↓   · 生成 checksums / 统计 / 审计记录

   备份包 olddisk-package/
```

### 5.2 恢复

```
备份包
 │
 ├─ ① 校验：sha256sum -c meta/checksums.sha256
 │
 ├─ ② 快照：pg_dump → backup.dump ；MinIO 全量 → minio/
 │
 ├─ ③ 建表：schema.sql（IF NOT EXISTS）+ 确保 uuid-ossp/pgcrypto
 │
 ├─ ④ 列对齐：按目标库真实列过滤/补齐
 │
 ├─ ⑤ 导入：单事务 BEGIN → DELETE(逆序) → INSERT×264 → COMMIT
 │           └─ 失败 → PG 自动 ROLLBACK → trap 用快照还原
 │
 ├─ ⑥ MinIO：按 storage_key 语义还原到各 bucket
 │
 ├─ ⑦ 配置：ai-config.json / ai-test-history.json（.env 不覆盖）
 │
 └─ ⑧ 独立验证：行数 / 桶数 / checksum / 关联
```

## 6. 数据语义：SSE 特有的坑

这些是从 **SSE 源码核实**得出的，不是猜的。

### 6.1 `storage_key` 带双重 bucket 前缀

```ts
// packages/api/src/routes/experiments.ts
const storageKey = `invoices/${req.params.id}/${itemId}_${Date.now()}.${ext}`;
await minio.upload(storageKey, 'invoices', ...);   // → putObject(bucket='invoices', key=storageKey)
```

⇒ 磁盘全路径 = `bucket + '/' + storage_key`：

```
storage_key (DB) : invoices/1081eb9b-…/xxx.pdf
bucket      (DB) : invoices
磁盘全路径        : invoices/invoices/1081eb9b-…/xxx.pdf   ← 双层
```

> 早期注释断言"storage_key 本身是完整 object key，不要再拼 bucket" —— **是错的**。

### 6.2 `avatar_url` 不拼 bucket

```ts
await minio.getObject(user.avatarUrl, 'avatars');   // bucket='avatars', key=avatar_url
```

`users.avatar_url` 存的是 MinIO 的 **key**（不含 bucket），
所以头像比对时**不能**再拼一层。

### 6.3 `approval_records.approver_id` 的角色→UUID 漂移

旧盘线上实际是 `character varying(50)`，存角色名：

```
admin / finance
```

但旧盘自己的 migration 文件写的是 `UUID`，当前 SSE 的 migration 已改回
`uuid REFERENCES users(id)`。直接导会报：

```
invalid input syntax for type uuid: "finance"
```

**权威映射来源** = `approval_rules.approval_chain`：

```json
{"role": "admin",   "assigneeId": "3e856835-07c0-41b8-9ae1-f33ef17ce80c", "assigneeName": "系统管理员"}
{"role": "finance", "assigneeId": "a7e2c5f4-3e15-4197-bb8f-7c36456b4cf1", "assigneeName": "王钰"}
```

比"按 `users.role` 反查"准确 —— `admin` 角色有 2 个用户，但审批链指定了实际那个人。

映射结果写入 `meta/semantic_transform.json`，**可审计**。

## 7. 质量保证

### 7.1 测试分层

| 层次 | 手段 | 覆盖 |
|---|---|---|
| 提取正确性 | 逐表 `count(*)` 交叉核对 | 不丢记录（物理行数 ≠ 记录数，必须用 CSV 解析器计数） |
| 提取无副作用 | 原 PGDATA 文件 mtime/内容比对 | 旧盘零写入 |
| 包完整性 | `meta/checksums.sha256` | 搬运后自检 |
| 导入正确性 | 独立验证器四类交叉校验 | 行数/桶数/checksum/关联 |
| 回滚能力 | 故意注入失败 + 状态比对 | DB 阶段、MinIO 阶段 |
| 分发完整性 | 逐文件 SHA-256 回读 | 复制不丢字节 |

### 7.2 防"假通过"

回滚测试最容易出的问题是**基线为空导致比较恒等**：

```bash
BEFORE_USERS=$(…)   # 空（目标库本来就没表）
AFTER_USERS=$(…)    # 空（回滚后确实没表）
[ "$BEFORE" = "$AFTER" ] → true → 报告"回滚成功"
```

实际上什么都没验证。已在 `test_rollback.sh` 中加**基线有效性断言**：
基线为空直接判 FAIL。
