# 导出功能设计 —— 旧盘 → 备份包

> 日期：2026-11-09 | 文档类型：功能设计
> 配套阅读：[01-设计说明.md](01-设计说明.md) · [06-踩坑与已知问题.md](06-踩坑与已知问题.md)

## 1. 功能边界

导出层负责把**旧盘上的原始存储**转成**可离线搬运的备份包**。

```
输入：旧盘挂载点（只读）
      ├── PostgreSQL PGDATA
      └── MinIO 数据目录
输出：olddisk-package/（纯文件目录，含 checksum）
```

**不负责**：目标库的列对齐、语义转换、导入 —— 那些在构建层与恢复层。

---

## 2. 模块清单

| 模块 | 职责 | 依赖 |
|---|---|---|
| `probe_oldroot.py` | 探查旧盘结构，产出探查报告 | 标准库 |
| `pg_offline_export.py` | PGDATA → CSV + schema.sql | PostgreSQL 同 major 二进制 |
| `minio_offline_export.py` | MinIO 数据目录 → 原始对象 | `msgpack` |
| `xlmeta_parse.py` | xl.meta v2 解析库（可独立复用） | `msgpack` |
| `xlmeta_probe.py` | xl.meta 结构探查/调试 | `msgpack` |
| `build_import_package.py` | 清洗 + 打包 | 标准库 |

## 3. 探查阶段（`probe_oldroot.py`）

### 3.1 目的

在动手提取之前，先摸清旧盘上**有什么、在哪里、多大、什么版本**。
这一步不能跳过 —— 旧盘的卷名、路径布局在不同机器上可能完全不同。

### 3.2 探测内容

```
probe_postgres(oldroot)     找 PGDATA：识别 PG_VERSION、找 postgresql.conf、
                            列出 base/ 下的数据库、统计文件数与体积
probe_minio(oldroot)        找 MinIO 数据目录：识别 .minio.sys、
                            列出 bucket、统计对象数与体积
probe_configs(oldroot)      找配置文件：.env、ai-config.json、docker-compose.yml
probe_docker_layout(oldroot) 找 docker 卷布局与挂载信息
```

### 3.3 输出

产出 `probe_report.json`（以及可选的 `.clean.json` 清洗版），内容：

| 字段 | 含义 |
|---|---|
| `postgres.pg_version` | 如 `"16"` —— 决定用哪个 major 的二进制 |
| `postgres.databases` | 库名列表 |
| `postgres.file_count` / `size_bytes` | PGDATA 文件数与体积 |
| `minio.buckets` | bucket 列表与对象数 |
| `configs` | 找到的配置文件路径 |

### 3.4 使用

```bash
python3 tools/probe_oldroot.py --root /path/to/oldroot --out probe_report.json
```

> **实测**：本项目实例中，旧盘根是 `/home/szl/oldroot`（**不是** `/oldroot`）。
> 卷名 `sse_pgdata` / `sse_miniodata` 与新系统同名，但数据不同
> （旧盘 `users` 7 行，新系统 1 行）。

## 4. PostgreSQL 离线提取（`pg_offline_export.py`）

### 4.1 原理

用 PostgreSQL 的**单用户模式**（`postgres --single`）在 PGDATA 副本上执行 SQL，
把表数据导成 CSV。

单用户模式的性质：

- 不监听网络端口，不需要 `postmaster` 守护进程
- 不做 checkpoint，不写 WAL
- **但会写少量文件**（`pg_control`、`pg_wal`、`pg_xact` 等）→ 必须用副本

### 4.2 执行流程

```
① 校验 --pgbin 的 postgres 版本 major == PGDATA/PG_VERSION 的 major
     不一致 → 直接拒绝（避免用错版本损坏副本）

② 复制 PGDATA → --workdir（默认 /tmp 下的临时目录）
     shutil.copytree(symlinks=True)
     跳过不需要的大文件（可选）

③ 通过单用户模式执行 SQL：
     postgres --single -D <workdir> <dbname>

   3a. 探测表清单：
       COPY (SELECT c.relname FROM pg_class c …) TO '<work>/tables.txt'
       —— 必须用【服务端】COPY，因为单用户模式下 \copy（客户端复制）不可用

   3b. 逐表导出：
       COPY (SELECT * FROM <table>) TO '<work>/<table>.csv'
       WITH (FORMAT csv, HEADER, NULL '\N')

④ 读回 CSV，按 schema.sql 的列定义生成单行 INSERT
⑤ 清理临时副本（除非 --keep-work）
```

### 4.3 关键实现细节

**服务端 COPY 的路径要绝对路径**：

```python
# 单用户模式下 postgres 进程以当前用户身份运行，
# 服务端 COPY 只能写当前用户有权限的路径
sql = f"COPY (SELECT * FROM {table}) TO '{abs_dest}' WITH (FORMAT csv, HEADER, NULL '\\N')"
```

**NULL 标记**：

```sql
COPY … WITH (FORMAT csv, HEADER, NULL '\N')
```

默认 COPY 把 NULL 输出成空字段，于是 `parent_id`（NULL）和 `password_hash`（''）
完全无法分辨。加 `NULL '\N'` 后：NULL → `\N`，空字符串 → 空字段，二者严格可区分。

**行数必须按 CSV 记录数统计**：

`system_messages.body`、`notification_logs.body` 这类字段含换行，
一条记录占多个物理行：

```
notification_logs:  物理行 135  ← 用 wc -l 统计会虚高
                    实际记录 49  ← 用 csv.reader 统计才对
```

必须用 Python `csv.reader` 计数，并最终用 PostgreSQL 自身 `count(*)` 交叉核对。

**schema.sql 的生成**：

从 `information_schema.columns` 取列名、类型、默认值、是否可空，
拼成 `CREATE TABLE` 语句。**注意：不导出自定义约束**（UNIQUE/CHECK/FK）——
原因见 [06-踩坑与已知问题.md](06-踩坑与已知问题.md) 6.9。

### 4.4 CLI

```bash
python3 tools/pg_offline_export.py \
    --pgdata   /path/to/oldroot/.../sse_pgdata \
    --outdir   olddisk-recovered/pg-export \
    --pgbin    /path/to/postgresql/16/bin \
    --dbname   sse \
    [--tables  users,invoices,...]   # 留空 = 自动探测
    [--workdir /tmp/pgdata-work]     # 临时副本位置
    [--keep-work]                    # 保留副本（调试用）
```

| 参数 | 说明 |
|---|---|
| `--pgdata` | 旧盘上的 PGDATA 目录（**只读**，脚本内部会先复制） |
| `--pgbin` | 与 PGDATA **同 major 版本**的 PostgreSQL `bin` 目录 |
| `--dbname` | 要导出的数据库名 |
| `--tables` | 逗号分隔表名，留空 = 自动探测 |
| `--outdir` | 导出目标目录 |
| `--workdir` / `--keep-work` | 临时副本位置 / 是否保留（调试用） |

### 4.5 版本约束（重要）

**二进制 major 版本必须与 PGDATA 一致。**

旧盘实例是 PostgreSQL **16**（`PG_VERSION` 文件内容为 `16`），
必须用 PostgreSQL 16.x 的 `postgres` 二进制。

跨 major 使用会导致副本启动失败或行为异常。工具会主动校验并拒绝。

> **ICU 依赖问题**：Debian 打包的 PostgreSQL 16 链接 ICU 72，
> 而 Ubuntu 24.04 系统自带 ICU 78，直接跑会报
> `libicui18n.so.72: cannot open shared object file`。
>
> 三种解法：
> 1. 用 Alpine 版 postgres 镜像（ICU 版本齐全）
> 2. 解包 ICU 72 的 `.deb`，用 `LD_LIBRARY_PATH` 指过去
> 3. **不重新提取** —— 只导入已构建好的包时完全不需要 ICU

## 5. MinIO 离线提取（`minio_offline_export.py`）

### 5.1 原理

MinIO 没有"离线导出对象"的官方工具。做法是**逆向解析**每个对象的
元数据文件 `xl.meta`，据此定位对象内容。

### 5.2 xl.meta v2 格式（逆向成果）

```
魔数：584c3220  /  ASCII "XL2 "
编码：msgpack
entries 起始 offset：8
```

顶层结构（`obj[0]` 是嵌套 msgpack = 完整的 `V2Obj` stat）：

| 索引 | 含义 |
|---|---|
| `[0]` | 嵌套 msgpack —— 完整 `V2Obj` stat |
| `[1]` | 版本 |
| `[2]` | flags |
| `[3]` | 数据 dict |

**stat 里的关键字段**：

| 字段 | 含义 |
|---|---|
| `Size` | 对象字节数 |
| `MTime` | 修改时间 |
| `MetaSys` | 系统元数据 —— **决定对象内容在哪** |
| `MetaUsr` | 用户元数据 |
| `ETag` | 内容指纹 |
| `DDir` | 大对象的目录 UUID（16 字节二进制） |

### 5.3 两种内容布局

| 类型 | 判据 | 内容位置 |
|---|---|---|
| **内联（小对象）** | `MetaSys` 含 `x-minio-internal-inline-data=true` | 内联在 `xl.meta` 里 |
| **外置（大对象）** | `MetaSys` 为空 | `<objdir>/<DDir-UUID>/part.N` |

**内联 payload 边界推导**（不靠文件魔数、不靠搜特征字节）：

```
header_len = len(inline_blob) - stat.Size   # 实测恒为 32 字节
payload    = inline_blob[header_len:]
```

原理：inline blob 里除了 payload 还带一段定长头部，头部长度 = blob 长度 − 实际大小。

**外置对象的两种目录布局**：

```
旧式: <objdir>/part.1
新式: <objdir>/<DDir-hex>/part.1     ← DDir 来自 stat
```

**DDir 的 UUID 表示陷阱**：

```
xl.meta 里:   0ac8cd6854564479a91dffdac10adb97   ← bytes.hex()，32 字符无连字符
磁盘目录名:   0ac8cd68-5456-4479-a91d-ffdac10adb97 ← uuid.UUID()，带连字符
```

必须用 `uuid.UUID(bytes=ddir)` 转换后再拼路径，直接用 hex 会找不到目录。

### 5.4 msgpack 解析陷阱

`xl.meta` 尾部带 padding，用 `msgpack.unpackb` 会失败：

```python
# ❌ 报错
msgpack.unpackb(raw)

# ✅ 用 Unpacker 流式解包，自动跳过 padding
unpacker = msgpack.Unpacker()
unpacker.feed(raw)
entries = list(unpacker)
```

### 5.5 导出流程

```
① 遍历数据目录 → 找到所有 xl.meta
② 解析每个 xl.meta → stat
③ 判断内联/外置 → 定位内容
④ 内容按【原始目录结构】写入 outdir/
     <outdir>/<bucket>/<key path>/<文件名>
     ← 保留 bucket/key 的层级，与 storage_key 语义直接对应
⑤ 记录导出清单：bucket、key、size、etag、来源（inline/part.N）、错误信息
```

### 5.6 CLI

```bash
python3 tools/minio_offline_export.py \
    --datadir /path/to/oldroot/.../sse_miniodata \
    --outdir   olddisk-recovered/minio-export \
    [--buckets invoices,payment-receipts,avatars]   # 留空 = 全部
    [--dry-run]                                       # 只扫描不写文件
```

| 参数 | 说明 |
|---|---|
| `--datadir` | MinIO 数据目录（**含 `.minio.sys` 的那一层**） |
| `--outdir` | 导出目标目录 |
| `--buckets` | 逗号分隔 bucket 白名单，留空 = 全部 |
| `--dry-run` | 只扫描不写文件，先看会导出什么 |

### 5.7 依赖

```bash
pip install msgpack
```

**实测版本**：`msgpack 1.0.3`，Python 3.10.12。

### 5.8 为什么不能直接拷目录

MinIO 的 `_minio.sys` 和对象目录**不能直接混入新版本**：

- `_minio.sys` 是运行时元数据（版本相关、格式内部）
- 新版 MinIO 的磁盘格式可能已变化
- 直接拷过去，轻则对象读不出，重则启动失败

必须通过解析器**提取出对象原始字节**，再由恢复层写进新 MinIO。

## 6. 打包（`build_import_package.py`）

### 6.1 职责

把"原始提取结果"变成"语义干净、可直接导入的备份包"。

```
olddisk-recovered/          →    olddisk-package/
├── pg-export/                    ├── pg/
│   ├── schema.sql                │   ├── schema.sql
│   ├── db/*.csv                  │   └── table_<name>.sql
│   └── db_row_counts.json        ├── minio/     (原样拷贝)
├── minio-export/                 ├── meta/
└── config/                       └── files/
```

### 6.2 CSV → 单行 INSERT

这是打包阶段最核心的转换。

```python
def sql_lit(s):
    """生成 PostgreSQL 字面量，处理换行/引号/反斜杠。"""
    # 统一用 E'...' 形式，保证一条 INSERT 只占一个物理行
```

处理要点：

| 要点 | 处理 |
|---|---|
| 含换行的字段 | `E'...\n...'` 转义 |
| 含单引号 | `''` 或 `\'`（配合 E'' 形式） |
| 含反斜杠 | `E'...\\...'` 双写 |
| NULL | SQL `NULL` 关键字，不是字符串 `'NULL'` |
| 数组列（`text[]`） | 按数组字面量生成，元素含逗号/花括号/空格时逐个加双引号 |

### 6.3 语义转换

角色名 → UUID 的转换由 `transform_approver_id.py` 独立完成，
产物写进 `meta/semantic_transform.json`：

```json
{
  "approval_records.approver_id": {
    "admin":   "3e856835-07c0-41b8-9ae1-f33ef17ce80c",
    "finance": "a7e2c5f4-3e15-4197-bb8f-7c36456b4cf1"
  },
  "source": "approval_rules.approval_chain.assigneeId"
}
```

**映射来源的解析**：`approval_chain` 是 JSON 字符串，值里带 SQL quoting 和额外转义，
所以解析器必须同时支持普通字符串 `'...'` 和 E 字符串 `E'...'` 两种字面量。

### 6.4 列元数据查询

`colmeta.sql` 是独立文件（不内嵌在 shell 里）：

```sql
-- 输出目标库每张表的列清单，供 filter_insert_columns.py 对齐
SELECT table_name, column_name, data_type, is_nullable, column_default, ordinal_position
FROM information_schema.columns
WHERE table_schema = 'public'
ORDER BY table_name, ordinal_position;
```

> 早期把它内嵌在 bash heredoc 里，因转义问题报
> `ERROR: syntax error at end of input` —— 独立成文件最稳。

### 6.5 CLI

```bash
python3 tools/build_import_package.py \
    --recovered   olddisk-recovered/ \
    --outdir      olddisk-package/ \
    --schema      olddisk-recovered/pg-export/schema.sql \
    [--source-host 192.168.3.107]
```

## 7. 输出的元数据清单

| 文件 | 内容 | 用途 |
|---|---|---|
| `manifest.json` | 包级信息：版本、来源、统计 | 快速了解这个包是什么 |
| `meta/checksums.sha256` | 全部文件 SHA-256（不含自身） | **搬运后自检** |
| `meta/table_counts.txt` | 每表行数 | 与导入后对比 |
| `meta/minio_counts.txt` | 每桶对象数 | 与导入后对比 |
| `meta/tables_present.txt` | 实际提取到的表 | 识别"导出中不存在"而跳过的表 |
| `meta/semantic_transform.json` | 语义转换记录 | **审计** |
| `meta/link_check.txt.*` | 数据库↔对象关联引用统计 | 验证引用完整性 |
| `meta/export_meta.sh` | 导出源环境 | 溯源 |

### 7.1 checksums.sha256 的用法

```bash
cd olddisk-package
sha256sum -c meta/checksums.sha256
# 44 个文件应全部 ": OK"
```

生成方式：

```bash
find . -type f ! -path './meta/checksums.sha256' -print0 \
  | sort -z | xargs -0 sha256sum > meta/checksums.sha256
```

> **注意**：注入故障做回滚测试后，包内容变了，**必须重算 checksum**，
> 否则导入脚本的完整性校验会先拒绝。

## 8. 实测结果

```
PostgreSQL 16  →  16 张表全部提取，264 行（15 张业务表有数据）
MinIO          →  16/16 对象，3 bucket（invoices 8 / payment-receipts 3 / avatars 5），0 错误
原 PGDATA      →  1379 个文件 0 修改（ext4 ro 挂载）
```

**表行数明细**：

```
expense_categories=8      reasoning_rules=1        approval_rules=3
mcp_api_keys=5             ontology_snapshots=77    notification_logs=49
notification_deliveries=68 system_messages=13      payment_audit_logs=3
users=7                    expense_reports=4        expense_items=11

```

导入时按"导出中不存在"跳过。
