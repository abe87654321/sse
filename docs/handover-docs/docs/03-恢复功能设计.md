## 1. 功能边界

恢复层负责把**备份包**安全地放进**运行中的目标系统**，并保证失败能还原。

```
输入：备份包 olddisk-package/
      目标 PostgreSQL 库
      目标 MinIO
输出：目标系统装载了备份包的数据
      ＋ 导入前快照（.rollback-<时间戳>/）
      ＋ 独立验证报告
```

## 3. 导入流程（`import_sse_data.sh`）

### 3.1 八个阶段

```
1/8  备份目标数据库        pg_dump → .rollback-<ts>/backup.dump
2/8  备份目标 MinIO        3 个 bucket 全量 → .rollback-<ts>/minio/
3/8  导入 PostgreSQL 数据  ★ 核心：建表 → 对齐 → 单事务导入
4/8  导入 MinIO 对象       按 storage_key 语义还原
5/8  导入配置文件          ai-config.json / ai-test-history.json（.env 不覆盖）
6/8  导入后验证            内建轻量校验
7/8  清理临时文件
8/8  完成
```

失败时进入**回滚流程**（第 4 节）。

### 3.2 CLI

```bash
bash tools/import_sse_data.sh --from <备份包目录> --target-db <库名> \
     [--dry-run] [--skip-minio] [--skip-files] [--keep-backup|--no-keep-backup]
```

| 参数 | 说明 |
|---|---|
| `--from` | 备份包目录（**必填**） |
| `--target-db` | 目标数据库名（**必填**） |
| `--dry-run` | 只做校验与预演，不实际写入 |
| `--skip-minio` | 跳过 MinIO 部分 |
| `--skip-files` | 跳过配置文件部分 |
| `--keep-backup` / `--no-keep-backup` | 是否保留回滚备份目录（默认保留） |

### 3.3 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `PG_CONTAINER` | 空 | **非空则走容器模式**（`docker exec`），宿主机无需装 psql |
| `DB_HOST` | `localhost` | |
| `DB_PORT` | `5433` | SSE 默认映射端口 |
| `DB_NAME` | — | 目标库（也可由 `--target-db` 给） |
| `DB_USER` | `sse` | |
| `DB_PASSWORD` | `sse_dev` | |
| `MINIO_ENDPOINT` | `localhost` | |
| `MINIO_PORT` | `9002` | |
| `MINIO_ACCESS_KEY` | `minioadmin` | |
| `MINIO_SECRET_KEY` | `minioadmin` | |
| `SSE_DIR` | — | SSE 部署目录（配置文件落到这里） |
| `MC_ALIAS` | `sse-import` | mc 别名 |

### 3.4 阶段 1：数据库备份

```bash
pg_dump -h <host> -p <port> -U <user> -d <db> \
       --format=custom --compress=9 --no-owner --no-privileges \
       -f <backup_dir>/backup.dump
```

用 **custom 格式**（`--format=custom`）：可压缩、可 `pg_restore` 选择性恢复。
`--compress=9` 是 zlib 最高压缩级 —— 实测 52K 的备份里含 16 个 TABLE DATA。

> **容器模式的坑**：`pg_dump` 的 custom 格式要求**可 seek 的文件**，
> 不能重定向到 stdout。必须：
> ```bash
> docker exec <容器> pg_dump -U <user> -d <db> --format=custom -f /tmp/sse_dump_$$.dump
> docker cp <容器>:/tmp/sse_dump_$$.dump <宿主机路径>
> docker exec <容器> rm -f /tmp/sse_dump_$$.dump
> ```

### 3.5 阶段 2：MinIO 备份

```bash
mc alias set sse-import "http://$MINIO_ENDPOINT:$MINIO_PORT" "$MINIO_ACCESS_KEY" "$MINIO_SECRET_KEY"
for b in invoices payment-receipts avatars; do
  mc mirror --overwrite "sse-import/$b" "$backup_dir/minio/$b"
done
```

### 3.6 阶段 3：导入 PostgreSQL（核心）

#### 3.6.1 建表

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS "pgcrypto";
```

> **必须先建扩展**：`uuid_generate_v4()` 这类函数依赖扩展；
> 而且回滚时的 `DROP SCHEMA public CASCADE` 会连带删掉装在 public 里的扩展，
> 所以建表前和回滚后都要补建。

然后把 `schema.sql` 里的 `CREATE TABLE` 改写成 `CREATE TABLE IF NOT EXISTS` 再执行：

```bash
sed -E -e 's/^CREATE TABLE public\.([a-z_]+) \(/CREATE TABLE IF NOT EXISTS public.\1 (/' \
    schema.sql > schema_tmp.sql
```

**不导自定义约束**：离线提取的 `schema.sql` 只有列/类型/默认值，
没有 UNIQUE/CHECK/FK —— 目标库自己的 migration 才是约束的权威来源。

#### 3.6.2 列对齐

```bash
# 取目标库真实列
psql … -f colmeta.sql -tAc "…" > 目标列清单
# 按目标列过滤/补齐 INSERT
python3 filter_insert_columns.py …
```

规则见 [01-设计说明.md](01-设计说明.md) 4.4。

**关键行为**：目标库 NOT NULL 且无默认值的缺失列 → **直接失败**，
不静默丢数据。

#### 3.6.3 单事务导入

这是整个恢复流程的核心安全性设计。

```sql
BEGIN;
-- 按【导入顺序的逆序】DELETE
DO $$ BEGIN IF EXISTS (SELECT 1 FROM information_schema.tables …) THEN
   DELETE FROM public.users; END IF; END $$;
… （逆序逐表）
-- 逐表 INSERT
INSERT INTO public.users (…) VALUES (…);
… （264 条）
COMMIT;
```

**为什么删除要按逆序**：否则 `DELETE FROM users` 会被外键约束挡住。

**为什么不用 TRUNCATE … CASCADE**：那会级联清空别的表，超出"重置本次导入的表"的范围。

**为什么必须单事务**：中途任何一条 INSERT 失败（比如类型不兼容），
PostgreSQL 自动 ROLLBACK，**目标库回到导入前状态**，不留半截数据。

#### 3.6.4 MinIO 导入

按 `storage_key` 语义还原，注意两条硬规则：

```
invoices/<storage_key>          →  bucket=invoices,  key=invoices/<storage_key>
payment-receipts/<storage_key>  →  bucket=payment-receipts, key=payment-receipts/<storage_key>
avatars/<avatar_url>            →  bucket=avatars, key=<avatar_url>   ← 不重复拼 bucket
```

备份包里文件已按原始目录结构存放，所以映射是机械的：

```
备份包 minio/invoices/invoices/<id>/<file>.pdf
  → mc cp 到 sse-import/invoices/invoices/<id>/<file>.pdf
```

### 3.7 阶段 5：配置文件

```bash
cp ai-config.json      $SSE_DIR/ai-config.json
cp ai-test-history.json $SSE_DIR/ai-test-history.json
# .env 只在目标不存在时复制（避免覆盖新系统的配置）
[ -f "$SSE_DIR/.env" ] && warn ".env 目标已存在，不覆盖" \
                       || cp env.local "$SSE_DIR/.env"
```

## 4. 回滚机制

### 4.1 触发条件

导入流程中任何一步返回非零 → `EXIT trap` 触发回滚。

### 4.2 回滚动作

```
① 回滚 MinIO
     for b in invoices payment-receipts avatars; do
       mc rm --recursive --force sse-import/$b
       mc mirror --overwrite <backup>/minio/$b sse-import/$b
     done

② 回滚 PostgreSQL
     psql -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
     psql -c "CREATE EXTENSION IF NOT EXISTS \"uuid-ossp\"; CREATE EXTENSION IF NOT EXISTS \"pgcrypto\";"
     pg_restore -d <db> --no-owner --no-privileges --clean --if-exists <backup>/backup.dump

③ 回滚配置文件
     从备份还原 ai-config.json / ai-test-history.json / .env
```

### 4.3 `pg_restore` 的参数陷阱（必读）

```bash
# ❌ 错：-f 是【输出】文件，不是输入文件
pg_restore -d mydb -f backup.dump
# → pg_restore: error: input file is too short (read 0, expected 5)

# ✅ 对：归档走【位置参数】
pg_restore -d mydb backup.dump
```

这个错误在容器模式里尤其隐蔽：`docker cp` 明明成功，`pg_restore` 却说"文件太短"。

### 4.4 回滚的已知限制

| 限制 | 说明 |
|---|---|
| `DROP SCHEMA public CASCADE` | 会删掉 public 下所有对象，包括扩展 → 回滚后必须补建扩展 |
| 目标库有备份之后新增的表 | 会被一并删掉（快照时刻不存在） |
| `pg_restore` 失败 | 磁盘满/权限问题会导致回滚本身失败 → 需人工介入 |

## 5. 独立验证（`verify_sse_restore.sh`）

### 5.1 设计原则

**验证器不复用导入脚本的任何中间产物** —— 它重新读备份包、重新查目标库、
重新算 checksum。这样才能发现"导入成功了但数据不对"。

### 5.2 四类交叉校验

```
① 表行数
   对每张表：备份包 meta/table_counts.txt  vs  目标库 count(*)
   实测：15/15 张表行数一致

② 桶对象数
   对每个 bucket：备份包统计  vs  目标 MinIO mc ls --recursive
   实测：3/3 个 bucket 一致

③ 对象内容 checksum
   对每个对象：备份包文件 SHA-256  vs  目标 MinIO 对象 SHA-256
   实测：16/16 个对象一致

④ 数据库↔对象关联
   从目标库取 storage_key / avatar_url，反查目标 MinIO 是否存在对应对象
   实测：15/15 条关联命中
```

第 ④ 项是最有价值的一项 —— 它验证的是**业务可用性**：
数据库里引用的附件确实能在 MinIO 里找到。

### 5.3 CLI

```bash
bash tools/verify_sse_restore.sh --from <备份包> --target-db <库名> [--verbose]
```

## 6. 回滚能力测试

### 6.1 为什么要有专门的测试

"回滚功能写了"不等于"回滚能用"。测试脚本通过**故意制造失败**来验证。

### 6.2 DB 阶段（`test_rollback.sh`）

```bash
bash tools/test_rollback.sh <备份包> <目标库> <SSE目录>
```

流程：

```
① 记录导入前基线（users / reasoning_rules 行数、MinIO 对象数）
② 复制备份包 → 注入故障（把 users.phone 置 NULL，触发 NOT NULL 冲突）
③ 重算包内 checksum（否则导入脚本的完整性校验会先拒绝）
④ 执行导入 → 预期失败 → 触发回滚
⑤ 比对导入后状态 vs 基线 → 必须完全一致
```

**故障注入方式的演变**：

| 版本 | 注入点 | 结果 |
|---|---|---|
| 初版 | 违反 `users_phone_key` 唯一约束 | ❌ **不触发** —— 离线提取的 schema.sql 不含自定义唯一约束 |
| 现行 | 违反 `NOT NULL` 约束 | ✅ 稳定触发（PostgreSQL 内建约束，任何目标库都有） |

#### 防"假通过"

```bash
# 基线为空时 before==after 都是空串 → 会误报"成功"
if [ -z "$BEFORE_USERS" ] || [ "$BEFORE_USERS" = "0" ]; then
  echo "  ❌ 基线无效：目标库 users 为空，无法验证回滚"
  FAIL=1
fi
```

**必须先跑一次正常导入建立基线**，否则这个测试无意义。

### 6.3 MinIO 阶段（`test_rollback_minio.sh`）

```bash
bash tools/test_rollback_minio.sh <备份包> <目标库> <SSE目录>
```

流程类似，但故障注入在 **MinIO 对象上传**环节：

```
① 在目标桶写入基线标记对象（动态发现基线 id，不写死）
② 注入 INJECT_MINIO_FAIL → bucket uploads 步骤失败
③ 触发回滚 → MinIO 应清空并从备份还原
④ 比对对象数与基线标记 → 必须一致
```

> ⚠️ 这两个测试会**真的在目标库和目标 MinIO 上操作**（导入 → 故意失败 → 回滚）。
> 跑之前确认当前状态可丢弃。**建议顺序：先跑回滚测试 → 再跑正式导入。**

## 7. 容器模式（宿主机无 psql）

### 7.1 开关

```bash
export PG_CONTAINER=sse-postgres-1
```

设置后，所有 PG 命令走 `docker exec`，宿主机**不需要安装任何东西**。

### 7.2 三条实现约束

| 约束 | 处理 |
|---|---|
| 宿主机 SQL 文件容器内不可见 | `docker exec -i … psql < file`（stdin 传输） |
| `pg_dump` custom 格式需可 seek 文件 | 容器内 `-f` 生成 → `docker cp` 取回 |
| `pg_restore` 归档走位置参数 | 见 4.3 |

### 7.3 容器里的 PostgreSQL 版本

必须与旧盘 major 一致。本项目实例：旧盘 PG 16，目标容器 `postgres:16-alpine`（16.15）✅。
