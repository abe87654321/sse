# SSE 智能报销系统多视角分析报告

> 分析范围：`README.md`、`packages/api`、`packages/auth`、`packages/mcp`、`packages/web`、`packages/db/src/migrations`。以下为静态代码审查结论，未启动系统做运行时验证；涉及审批、删除、SCIM 的结论建议用种子数据复测。

## 一、结论速览

| 视角 | 评价 | 一句话结论 |
|---|---|---|
| 系统管理员 | 6.5 / 10 | 日常用户、规则、AI 配置可用，但部门管理、密钥管理、审计台、备份与可观测性缺口明显 |
| 审计 | 4.5 / 10 | 付款与审批轨迹较好，但缺少通用审计日志、只读审计角色，且删除会销毁证据 |
| 普通操作者 | 7 / 10 | AI 填单、发票 OCR、审批核对体验是亮点；语音缺失、筛选/批量/委托等效率能力不足 |
| 外部系统输入 | 7 / 10 | MCP + OpenAPI 设计较好；SCIM/MDM 过于简化，存在角色提升风险 |
| 外部系统输出 | 4.5 / 10 | 通知可用，但没有出站事件/Webhook，导出能力与文档宣称不一致 |

**最需要优先处理的三件事**

1. 审批流中角色型步骤的审批人匹配存在前后端不一致，非管理员审批可能被后端拒绝。
2. 管理员删除已通过单据、级联删除用户会一并删除审批记录/付款审计，审计证据不可保留。
3. SCIM/MDM 可直接写入 `role`，仅靠共享静态令牌，且同步过程无审计、无角色白名单。

## 二、系统画像

- 架构：pnpm monorepo，Vue 3 SPA + Express API + PostgreSQL + MinIO；核心域独立，另有 MCP、SCIM/MDM、本体/Oxigraph 适配层。
- 角色：`employee / dept_approver / finance / admin`，权限矩阵见 `packages/auth/src/rbac.ts:12`。
- 主要输入面：Web 表单、AI 文本/截图/发票解析、REST、MCP、SCIM、MDM Webhook。
- 主要输出面：站内信、短信、邮件、CSV/JSON 统计导出、Ontology/SPARQL、OpenAPI。
- 已有审计资产：`approval_records`、`payment_audit_logs`、`notification_logs`、`identity_mappings`、发票核对结果、Ontology 快照/Outbox。

## 三、系统管理员视角

### 做得好的地方

- 用户生命周期较完整：新增、编辑、改角色、禁用、软删除、硬删除、级联删除都有入口（`packages/api/src/routes/admin.ts:103`、`admin.ts:193`、`admin.ts:252`）。
- 审批规则可视化配置：`WorkflowDesigner` + 规则增删改查（`packages/web/src/pages/Admin.vue:130`）。
- AI/OCR 引擎配置有模型目录、连通性测试、OCR 样例测试和历史记录（`admin.ts:446`、`admin.ts:601`）。
- 广播消息有发送与投递明细（`packages/api/src/routes/admin-messages.ts`）。
- 本体状态、推理规则预览、健康检查均有管理入口。
- 密码、登录限流、上传魔数校验、服务令牌常量时间比较等基础安全做得比一般小系统好。

### 关键不便与风险

| 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 部门管理实际不可用：新增部门不落库，删除接口不存在 | `admin.ts:412` 只返回名称不写表；`AdminDepartments.vue:84` 调 `DELETE /admin/departments/:name`，API 未定义该路由 | 管理员点“新增/删除”无效或 404 | 建立 `departments` 表；或明确部门来自用户字段并移除假入口 |
| MCP/API Key 无管理界面，只能手工 SQL 插入 | `migrations/009_mcp_api_keys.sql`；全仓库无 `/admin/mcp-keys` 路由 | 外部接入方开通/轮换/吊销困难，易长期泄漏 | 增加密钥列表、创建、过期、吊销、最近使用时间；数据库只存哈希 |
| 破坏性删除过强 | `expenses.ts:827` 管理员可删除非付款单据（含已通过）；`pg-user-repo.ts:99` 级联删除会删除付款单与付款审计 | 合规证据丢失 | 默认只允许软删除/作废；物理删除需双人审批并保留 tombstone |
| 配置分散在 `.env` 与 `ai-config.json` | `ai-engines.ts:20`、`ai-engines.ts:34` | 多实例配置漂移；密钥明文文件；变更无审计 | 配置入库并加密，增加版本与变更记录 |
| 缺少审计台、指标、备份、保留策略、会话管理、MFA | 无对应路由/页面；`health.ts` 仅返回基础健康 | 管理员无法发现异常、无法追责、无法证明可恢复 | 增加只读审计台、Prometheus 指标、备份状态、强制改密与 MFA |
| 本体 v2 只允许单 API 副本 | `README.md` 多副本会产生分叉图 | 扩容受限 | 引入共享图存储或明确单副本部署约束 |
| 默认管理员密码公开且策略偏弱 | `migrations/001_initial.sql:161`、`README.md:177`；密码最短 6 位 `password.ts:5` | 初始暴露风险 | 首次登录强制改密，提升密码策略 |
| 管理员同时具备审批与付款权限 | `rbac.ts:37`，`canApprove/canFinalize` 均为 true | 缺少职责分离 | 引入审计员/只读角色，生产环境限制 admin 操作业务 |

## 四、审计视角

### 当前能回答的问题

| 审计问题 | 是否可答 | 依据 |
|---|---|---|
| 谁在何时审批、意见是什么 | 可以 | `approval_records` 保留 step、approver、comment、时间 |
| 谁付款、改付款、撤销付款，原因是什么 | 可以，且质量较好 | `payment_audit_logs` 保存 `before/after/reason/operator`（`011_payment_receipts_audit.sql:21`） |
| 发票是否重复、金额是否不符 | 可以 | 发票核对与异常扫描 |
| 通知是否送达 | 可以 | `notification_logs` 与投递明细 |
| 已删除单据是否还能追溯 | 不能 | 删除会清空审批记录，级联删除会清空付款审计 |
| 谁改过报销金额/明细 | 不能 | 编辑直接覆盖，无字段级历史 |
| 谁查看/下载过发票、回单 | 不能 | 下载接口无访问审计 |
| 谁改过角色、规则、AI 配置 | 不能 | 无通用审计事件 |
| 谁导出过数据 | 不能 | 导出无审计 |
| MCP/Agent 做了什么 | 仅 stderr | `packages/mcp/src/server.ts:72`，未入库、可关闭、难检索 |

### 核心审计缺口

1. **没有通用审计日志表**
   全仓库只有 `payment_audit_logs`。用户、角色、规则、配置、登录、导出、下载、SCIM 同步、MCP 调用均无持久化审计。

2. **删除会销毁证据**
   `expenses.ts:827` 管理员删除已通过单据时直接删除 `approval_records`；`pg-user-repo.ts:99` 级联删除用户会删除其报销单、付款单和关联审计。`payment_audit_logs.report_id` 又是 `ON DELETE CASCADE`。这是审计视角的 P0。

3. **审批时没有固化单据快照**
   审批记录只记录审批动作，不记录当时的金额、明细、发票、规则版本。单据被驳回后修改再提交，旧审批记录仍指向同一 `report_id`，但内容已变，审计链断裂。

4. **核对结果被覆盖**
   重新核对时 `verification_result` 被重置/覆盖（`expenses.ts:748`、`expenses.ts:908`），没有历史版本，无法证明“审批时看到的核对结果”。

5. **缺少只读审计角色**
   只有员工/部门审批人/财务/管理员。审计人员只能借用财务或管理员账号，违反最小权限与职责分离。

6. **统计与导出不利于审计**
   - 导出只有 CSV/JSON，无明细、发票、审批链、付款信息（`statistics.ts:88`）。
   - 类别/部门/月度统计没有应用时间过滤，`department` 参数也未使用（`statistics.ts:30`）。
   - 前端没有导出入口，尽管 API 存在。
   - README 宣称 Excel 导出，实际没有 XLSX。

7. **无防篡改与保留策略**
   无哈希链、WORM、法律保留、保留期限、SIEM 输出。

## 五、普通操作者视角

### 亮点

- AI 填单覆盖文字、截图、发票三种输入，识别结果可编辑后填入表单（`ExpenseForm.vue:25`）。
- 发票按明细上传，支持 PDF/OFD；发票核对面板能提示金额、日期、票号、重复票。
- 审批页展示 AI 核对结果，差异需显式确认，设计上有利于减少误批。
- 付款回单、撤销、修改都有页面与原因记录。
- 站内消息、短信/邮件偏好、待办角标、移动端 FAB 等基础体验完整。

### 主要摩擦点

| 问题 | 证据 | 建议 |
|---|---|---|
| 没有语音输入，但 README 宣称 “Speak / 语音” | `ExpenseForm.vue:25` 只有文字/截图/发票；README 第 32、43 行 | 要么实现录音+转写，要么修正宣传 |
| 列表只支持状态+关键词，API 已有日期/金额/类别/申请人筛选 | `ExpenseList.vue:4` vs `expenses.ts:89` | 补齐筛选、排序、每页条数 |
| 无自动保存/草稿恢复 | 表单离开页面即丢失未保存内容 | 增加本地草稿与离开提醒 |
| 审批快捷操作未走核对确认流程 | `Approvals.vue:129` 直接 `{}` 审批，遇核对差异才报错 | 快捷审批前弹出核对摘要 |
| 非管理员审批可能失败 | 前端按 `approverId === role` 显示按钮（`ExpenseDetail.vue:240`），后端按 `approverId === userId` 匹配（`approvals.ts:126`），而引擎写入的是角色名（`approval-engine.ts:85`） | 统一为真实用户 ID，或后端按角色+部门匹配 |
| 员工也能看到“统计分析”导航，但接口仅财务/管理员 | `DefaultLayout.vue:119` vs `statistics.ts:16` | 导航按角色过滤；无权限页面给出解释 |
| 无批量提交/撤回/复制/周期性报销 | 无相关接口与页面 | 优先做批量与复制上月报销 |
| 审批人无委托/休假代理，仅 48/96 小时提醒升级 | 通知调度器有升级，无委托 | 增加审批委托与转交 |

## 六、外部系统输入/输出便利性

### 输入通道

| 通道 | 便利性 | 说明 |
|---|---|---|
| REST + JWT | 较好 | 接口齐全，角色/部门数据域在服务端强制 |
| OpenAPI 3.1 | 较好 | `GET /openapi.json`，适合非 MCP Agent；但只覆盖 Agent 向接口，不含 SCIM/管理/导出 |
| MCP | 强 | 22 个工具，stdio + Streamable HTTP + 旧 SSE；按 key 解析身份、限流、超时、stderr 审计 |
| SCIM 2.0 | 弱 | 仅 `POST/GET /scim/Users`，无 PATCH/PUT/DELETE、无 Groups、无标准分页；外部 HR 无法完整生命周期同步 |
| MDM Webhook | 弱 | 单事件接口，无签名/时间戳/重放保护，仅静态令牌 |
| 发票文件 | 较好 | PDF/OFD、魔数校验；MCP 支持发票直提 |
| 批量导入 | 缺失 | 无 CSV 批量导入用户/报销单 |

**输入侧关键风险**

- SCIM/MDM 可直接写入 `role`，令牌持有者可创建管理员（`identity-bridge.ts:31`、`identity-bridge.ts:79`）；建议角色白名单与 source→role 映射。
- SCIM/MDM 创建的用户密码是哨兵值 `!`，且仓库内没有 OIDC/SAML/SSO，导致这些用户无法登录，只能由管理员手工设密（`identity-bridge.ts:48`、`password.ts:8`）。
- API Key 明文入库、无创建/吊销界面、无 per-key scope、无最近使用记录。
- 通用 REST 无限流、无幂等键、无版本化；`cors()` 默认放开所有来源（`index.ts:50`）。
- `GET /categories` 无认证（`index.ts:69`），属于轻微信息暴露。
- 列表 `pageSize` 未设上限，存在大分页压力。

### 输出通道

| 通道 | 便利性 | 说明 |
|---|---|---|
| 站内信/短信/邮件 | 较好 | 事件覆盖审批、付款、广播；有投递追踪 |
| CSV/JSON 导出 | 一般 | 只有主单字段，无明细/发票/审批/付款；无 XLSX；无前端入口 |
| 出站 Webhook/事件订阅 | 缺失 | 审批通过、付款完成等事件无法推送给 ERP/财务系统，只能轮询 |
| Ontology/SPARQL | 较强 | 适合跨系统审计分析，但仅只读，且 v2 单副本约束 |
| OpenAPI/healthz | 较好 | 便于集成与探活；无 `/metrics` |
| 审计日志导出 | 缺失 | 外部审计系统无法获取结构化审计事件 |

**结论：** 输入侧“给 AI Agent 用”做得较好，但“给企业系统用”偏弱；输出侧最大的短板是没有出站事件与完整对账导出。财务/ERP 集成目前只能靠轮询 REST 或 MCP。

## 七、优先级清单

### P0：影响主流程或审计有效性

1. 修复审批人匹配：审批记录应写入真实用户 ID，或后端按角色+部门匹配（`approval-engine.ts:80`、`approvals.ts:102`）。
2. 禁止物理删除已通过/已付款单据及审批记录；用户删除改为停用/匿名化，保留业务与审计数据（`expenses.ts:827`、`pg-user-repo.ts:99`）。
3. SCIM/MDM 增加角色白名单、来源映射、请求签名与审计日志（`scim.ts`、`webhook.ts`、`identity-bridge.ts`）。
4. 建立 append-only 通用审计事件表，覆盖登录、增删改、导出、下载、配置、角色、身份同步、MCP 调用。

### P1：影响日常效率与合规可用性

5. 报销单内容快照：提交、每步审批、付款时保存不可变 JSON 快照。
6. 发票核对历史版本，不覆盖旧结果。
7. 导出补齐明细、审批链、付款、发票字段；增加 XLSX 与导出审计。
8. 修复统计过滤条件，确保类别/部门/月度与总览口径一致。
9. 实现真实部门 CRUD，或移除无效入口。
10. MCP Key 管理界面 + 哈希存储 + 过期/吊销/最后使用时间。
11. 导航按角色过滤，消除 403/空页面。
12. 增加只读审计员角色与审计查询页面。

### P2：体验与平台化

13. 语音输入或修正 README；Excel 导出或修正文档。
14. 列表筛选/排序/分页可配置；批量与复制报销。
15. 审批委托、批量审批、核对摘要前置。
16. 幂等键、API 版本化、CORS 白名单、通用限流。
17. Prometheus 指标、结构化日志、备份与保留策略、MFA。
18. 出站事件总线/Webhook，支持 ERP/财务系统订阅。

## 八、建议落地顺序

**第 1 阶段（1–2 周，止血）**
- 修审批匹配；用 4 个角色账号跑通“部门审批→财务审批→付款”。
- 关闭管理员删除已通过单据与级联删除入口。
- 给 SCIM/MDM 加角色白名单；轮换 SCIM/MDM 令牌。
- 移除或修正部门管理假入口、语音/Excel 宣传。

**第 2 阶段（1–2 月，可审计）**
- 上线 `audit_events` 与只读审计员角色。
- 报销单/核对结果快照；导出补齐并记审计。
- MCP Key 生命周期管理；密钥改哈希。
- 统计口径修复、导航权限修复、审计页面。

**第 3 阶段（2–3 月，可集成）**
- 出站事件/Webhook、完整 SCIM 生命周期、可选 OIDC。
- 审计日志 SIEM 输出、保留与法律保留、防篡改。
- 多副本本体方案、指标与备份演练。
